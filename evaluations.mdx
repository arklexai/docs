title: "Evaluations"
description: "Grade simulation conversations with their scenario assertions, and optionally score them with an LLM judge."
---

An evaluation grades the conversations from one simulation. Each conversation passes or fails based on its scenario's [assertions](/scenarios#assertions). You can also choose metrics for an LLM judge to score. Arklex then groups recurring problems into failure patterns, and reviewers can add their own scores with [annotations](/annotations).

<Note>
  New here? The [Quickstart](/quickstart) walks you through running your first evaluation end to end. This page is the full reference for every section and option.
</Note>

---

## See your evaluations

Go to **Evaluations** in the sidebar to see every evaluation in your organization.

<Frame>
  ![Evaluations list](/images/evaluation-table.png)
</Frame>

The list has these columns: **Evaluation Name**, **Simulations Evaluated**, **Created By**, **Date**, and **Status** (Completed, Running, Failed, or Cancelled). A badge on each name shows whether the evaluation scored the **Agent** or the **Simulated user**.

Use **Search** to filter by evaluation name, and **Filter** to narrow by **Created by me** or status. Click a row to open the evaluation once it has finished running.

## Create an evaluation

Click **New Evaluation** on the Evaluations page. You can also start one from an agent's **Evaluations** tab, which lists only that agent's simulations.

<Frame>
  ![New Evaluation form: name the run, pick a simulation, and select metrics.](/images/run-evaluation.png)
</Frame>

<ParamField path="Evaluate" type="string" required>
  What to score. **Agent** (the default) scores the agent you're testing. **Simulated user** scores the simulated user that played the customer. See [Evaluate the simulated user](#evaluate-the-simulated-user).
</ParamField>

<ParamField path="Evaluation Name" type="string" required>
  A name for this run, for example "Core Support identity and policy check".
</ParamField>

<ParamField path="Simulation" type="string" required>
  The simulation to evaluate. Only completed simulations can be evaluated. Search the list, or use **Filter** to show only simulations you created.
</ParamField>

<ParamField path="Metrics" type="array">
  The metrics the LLM judge scores. **Helpfulness**, **Coherence**, and **Relevance** are selected by default. Add or remove any built-in or custom metric. **Create Custom Metric** closes the form and opens the **Metrics** page. See [Metrics](/metrics).

  Each scenario's assertions always run and decide Pass or Fail, whatever metrics you pick. To check assertions only, clear every metric. See [Assertions-only evaluations](#assertions-only-evaluations).
</ParamField>

<ParamField path="Provider and Model" type="string" required>
  The LLM the judge uses for metrics and **LLM judge** assertions. Choose a **Model**. If your deployment offers more than one provider, choose the **Provider** first. A default is selected for you.
</ParamField>

Click **Run Evaluation** to start. The status changes to **Completed** when grading is done.

<Note>
  If the simulation captured tool calls and just finished, the evaluation waits until all tool calls are collected. This can take up to 5 minutes.
</Note>

### Assertions-only evaluations

An agent evaluation with no metrics checks each conversation's assertions and nothing else. The form shows "No metrics selected: only assertions will run." The results have an **Overview** with **Results** and **Failure patterns**, and a **Conversations** tab. There are no metric scores and no annotation tabs.

Use this for a quick pass or fail check, for example after you change your agent. Simulated-user evaluations always score their fixed metrics. Through the [API](/api), an evaluation needs at least one metric.

## Read an evaluation's results

The header shows the evaluation name and status. Below them, a line shows the agent and simulation (each links to its page), the judge model, and when the evaluation ran and who started it. While the evaluation runs, the header has a **Cancel Evaluation** button. After it finishes, the header has a **Re-evaluate** button.

The results are split into tabs:

| Tab | What it shows |
| --- | --- |
| **Overview** | Pass and fail results, metric scores, and failure patterns. |
| **Conversations** | Every conversation, with its result and scores. |
| **Annotations** | Reviewers' own scores next to the judge's. |
| **Annotation Calibration** | How often the judge agrees with your team. |

The **Annotations** and **Annotation Calibration** tabs appear only on agent evaluations that score at least one metric.

### Overview: results

**Results** opens with **Conversations passed**: how many conversations passed out of the total. Below it, a line counts how many failed, were inconclusive, had no assertions, or errored. A conversation passes when every assertion on its scenario passes.

Each conversation gets one of these results:

| Result | Meaning |
| --- | --- |
| **Pass** | Every assertion passed. |
| **Fail** | At least one assertion failed. |
| **Inconclusive** | Nothing failed, but at least one assertion couldn't be judged. For example, the conversation never reached that point, or tool call data was missing. |
| **No assertions** | The scenario has no assertions, so there's no Pass or Fail. Metrics can still score the conversation. |
| **Error** | The conversation errored during the simulation or the evaluation, so it wasn't graded. |

The **Failed** list shows each conversation that didn't pass, with its scenario name and how many assertions passed. When several kinds of assertion failed, use the **LLM judge**, **Text match**, and **Tool calls** chips to filter the list. Click a conversation to open it. If tool calls weren't captured on some turns, a warning says how many turns couldn't be checked.

If no scenario in the simulation has assertions, **Results** is replaced by a note that says to add assertions to get a Pass or Fail. See [Add assertions to existing scenarios](/scenarios#add-assertions-to-existing-scenarios).

### Overview: metrics

**Metrics** appears when the evaluation scores at least one metric. Metric scores describe quality. They don't change whether a conversation passed.

Metrics are grouped by scope:

- **Conversation scoped**: scored once for the whole conversation, after it ends.
- **Turn scoped**: scored on each agent reply. A conversation's score is the mean of its turns.

Within each group, numeric metrics come first, lowest score first. Each one shows:

- The average score out of the maximum, for example `3.4 /5`, and the median.
- A bar colored by how the average compares with the maximum: green for 80% or higher, blue for 60% to under 80%, amber for 40% to under 60%, and red below 40%.
- **Lowest**: up to three conversations that scored lowest. Click one to open it at its lowest turn.
- A link to the metric's failure patterns, if it has any.

Label metrics, such as **Agent Behavior Failure** or **Tool call behavior**, show how often each label was assigned. Expand a label to see where it was assigned, then click a conversation or a **Turn N** chip to open it.

### Overview: failure patterns

**Failure patterns** groups recurring problems across the conversations, so you can fix causes instead of single conversations. Patterns come from:

- **Failed assertions**.
- **Low metric scores**: a numeric score below 60% of the maximum (below 3 on a 1 to 5 scale), or a label that signals a problem.
- **Agent Behavior Failure** labels, when you select that metric.

Each pattern shows its severity (**Critical**, **High**, **Medium**, or **Low**), a description, its source and number of occurrences, and the conversations and turns where it appeared. Click a conversation to open it at the first flagged turn. Patterns from failed assertions are **High**.

Patterns are sorted by severity, with assertion patterns first within each severity, then by occurrences. Use the chips at the top to show one source, such as **Assertions** or a single metric. The first five patterns are shown. Click **Show all** to see the rest.

Assertions-only evaluations have failure patterns too, built from the failed assertions.

### Conversations

A table of every conversation:

| Column | Description |
| --- | --- |
| **Conv #** | The conversation number. |
| **Result** | The conversation's [result](#overview-results). |
| **Assertions** | How many of the scenario's assertions passed. |
| **Scenario Name** | The scenario that generated the conversation. |
| **Turns** | The number of exchanges. |
| **User Goal Completion** | Shown only when you select that metric. |
| One column per metric | The conversation's score. For a turn scoped metric, the mean across turns. Hover to see the lowest turn. |

Click **Columns** to show or hide metric columns. Your choice is remembered in this browser. Click **Load More** to see more than 100 conversations.

### Inspect a conversation

Click a conversation in any tab to open it. Use the left and right arrows to move between conversations. The conversation view has these parts, top to bottom:

- **Metrics**: collapsed by default. Shows the conversation scoped scores, and the mean and median of each turn scoped metric.
- **Assertions**: each assertion with its kind, what it checks, the reason for its result, and **Pass**, **Fail**, or **Inconclusive**. For **Tool calls** assertions, click **Show calls** to compare the expected calls with the actual, missing, and unexpected ones. This is where you see why a conversation failed.
- **Scenario**: the goal, profile, and knowledge behind the conversation. Click **Open scenario** to edit it.
- **Conversation Transcript**: click **metrics** under an agent turn to see that turn's scores. For a label, click the info icon to read the judge's reasoning.

Click **Download** to save the transcript as a text file, or **Comments** to discuss the conversation with your team. See [Add comments](/annotations#add-comments).

<Frame>
  ![Conversation view with a failed assertion and the reason it failed](/images/evaluation-convo-view.png)
</Frame>

### Annotations and calibration

On the **Annotations** tab, reviewers score turns or whole conversations without overwriting the judge's scores. **Annotation Calibration** shows how often the judge agrees with your team's resolved scores, for each metric. See [Annotations](/annotations).

## Evaluate the simulated user

A simulated-user evaluation checks how well the simulated user played its part, so you can trust your simulation results. Set **Evaluate** to **Simulated user** when you create the evaluation. These evaluations always score three fixed metrics: **Character Consistency**, **Goal Adherence**, and **Realism**.

The results have two tabs:

- **Overview**: **Metrics** shows how often the simulated user **Stays on persona**, how many **Conversations kept on goal**, how often **Required sub-goals raised**, and how often it **Passes for a real user**, each as passed out of checked. Higher is better. **Failure patterns** shows how often each problem the judge looks for showed up. Lower is better. Expand a row to see the conversations.
- **Conversations**: a table with **Conv #**, **Scenario Name**, **In character**, **Off-goal turns**, **Required sub-goals**, and **Issues** for each conversation.

Simulated-user evaluations don't have annotation tabs.

## Re-evaluate

To grade the same conversations again, open the menu on an evaluation row and select **Re-evaluate**, or click **Re-evaluate** on the detail page. Edit the **Evaluation name** to tell the runs apart, then click **Run Evaluation**.

Re-evaluating creates a new evaluation with the same simulation, metrics, and model. An assertions-only evaluation is re-evaluated without metrics. The original evaluation and its annotations stay unchanged. It uses the metric versions from the original run, so later edits to a metric aren't applied. To score with your updated metrics, create a new evaluation instead.

If the evaluation uses metrics that call MCP tools, choose how to handle tool results:

- **Use saved tool results**: scores again against the tool results the original run stored. Your systems aren't called.
- **Fetch new tool results**: calls your MCP tools again, to check whether the results still hold.

---

## Cancel or delete an evaluation

Open the menu on an evaluation row:

- **Cancel**: stops an evaluation that is still running.
- **Delete**: removes the evaluation and its annotations after you confirm. You can't delete an evaluation while it's running.

## FAQ

<AccordionGroup>
  <Accordion title="Can an evaluation cover multiple simulations?">
    No. Each evaluation grades one simulation, which the **Simulations Evaluated** column shows. To compare simulations, create one evaluation per simulation with the same metrics and model. Through the API, you can also score conversations you already have without running a simulation. See [API overview](/api).
  </Accordion>

  <Accordion title="How do I improve a metric that consistently scores low?">
    Click the metric's failure patterns link on the **Overview**, or open its **Lowest** conversations, to find the pattern. Update your agent's system prompt, knowledge, or configuration to address the root cause. Then run a new simulation and evaluation to confirm the improvement.
  </Accordion>
</AccordionGroup>
